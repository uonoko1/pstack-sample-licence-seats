# pstack-sample-licence-seats

[pstack](https://github.com/cursor/plugins/tree/main/pstack)（AI コーディングエージェント用スキルパック）の効果を確かめるための検証用サンプルです。
同じ依頼を「pstack あり」と「pstack なし」で実装し、結果を比べます。

## 題材：ライセンス席数マネージャー

スペースのライセンス席数を管理する Scala 3 のライブラリです。永続化はせず、インメモリで動きます。

- プランは Free（10 席）、Starter（30 席）、Standard（無制限）
- ユーザーへのライセンス付与と剥奪、プラン変更を扱う
- 上限を超える付与は拒否する
- 現在の利用数が上限を上回るプランへのダウングレードは受け付け、14 日間の猶予期間を始める
  - 超過しているあいだ付与は拒否し、剥奪は常に受け付ける。上限内に収まれば通常の状態に戻る
  - 14 日過ぎても超過していればスペースは停止状態になり、利用数がまだ上回るプランへの変更は拒否する
  - 現在時刻は呼び出し側がリクエストごとに渡す（ライブラリはシステム時計を読まない）
- 同じリクエスト ID の再送は同じ結果を返す
- 並行に付与しても上限を超えない

## ラウンド

| ラウンド | 依頼 | 見るところ |
| --- | --- | --- |
| 1. 新規 | 上の仕様で実装 | 型の設計、テストが振る舞いを見ているか |
| 2. 仕様変更 | 「猶予期間 14 日」を追加 | 継ぎ足しになるか、設計し直すか |
| 3. バグ | 「付与が 11 件成功し、1 人は保有者にいない」と報告 | 再現してから直すか、根本原因か |

### ラウンド 1 の依頼文

> Scala 3 と sbt で、スペースのライセンス席数を管理するライブラリを作って。
> ゴール: プラン（Free=10席, Starter=30席, Standard=無制限）、ユーザーへのライセンス付与・剥奪、プラン変更を扱える。
> ルール: 上限を超える付与は拒否。上限を下回るプランへのダウングレードは拒否。同じリクエスト ID の再送は同じ結果を返す。並行に付与しても上限を超えない。
> 確認方法: sbt test が通ること。並行付与のテストと、再送のテストを含むこと。永続化は不要でインメモリでよい。

`pstack` 側はこの依頼文の先頭に `/pstack:poteto-mode` を付けたものに相当します。

## ラウンド 1 の結果

| | `plain` | `pstack` |
| --- | --- | --- |
| 本体 / テストの行数 | 131 / 222 | 91 / 243 |
| テスト件数 | 20 | 25 |
| コミット数 | 1 | 9 |
| 拒否理由の種類 | 5 | 3 |
| 使ったサブエージェント | 1（約 7 万トークン、約 2 分） | 3（合計約 32 万トークン、最長約 8 分）と統合作業 |

- 設計の骨格は両方とも同じになった。純粋な状態遷移関数がすべてのルールを持ち、`AtomicReference` を持つ薄いクラスが compare-and-set で適用する。
- `pstack` は付与と剥奪を「最終状態の指定」として扱い、付与済みユーザーへの再付与や未付与ユーザーの剥奪を成功にした。`plain` はこれらを拒否する。
- `pstack` は fable の候補を土台にし、opus の候補から「同じリクエスト ID を別のコマンドで使い回したら拒否する」を移植した。
- 親モデルの候補にあった `SeatLimit.Limited` のコンストラクタを package private にする保護は、移植しなかった。テストで確かめたところ、Scala 3.3.6 では `new SeatLimit.Limited(-1)` は拒否されるが `SeatLimit.Limited(-1)` は通り、保護になっていなかった。
- 並行付与のテストは、どちらのブランチでも、適用を非アトミックに書き換えると失敗することを確認している。

## ラウンド 2 の結果

依頼は「上限を上回るダウングレードは拒否せず、14 日の猶予期間を始める。期限を過ぎても超過していたら停止状態にする。時刻は呼び出し側が渡す」。

| | `plain` | `pstack` |
| --- | --- | --- |
| `src` の差分 | 4 ファイル、+301 / −67 | 5 ファイル、+166 / −36 |
| 本体 / テストの行数 | 188 / 399 | 121 / 343 |
| テスト件数 | 34 | 32 |
| このラウンドのコミット数 | 1 | 6 |
| 使ったサブエージェント | 1（約 9 万トークン、約 2 分） | 3（合計約 39 万トークン、最長約 10 分）と統合作業 |

- 設計はまた同じ形になった。期限を `Option[Instant]` として状態に 1 つだけ持ち、受け付けた遷移のたびに 1 か所でプランと保有者数から導く。停止かどうかは保存せず、期限と時刻から計算する。
- `pstack` の 3 候補はほぼ同一のコードに収束したので、移植はせず、差分が最も小さい opus の候補をそのまま採用した。
- `pstack` は、意味を失った古い拒否理由を最初のコミットで消してから、時刻、期限、停止の順に 1 つずつ足している。`plain` は 1 コミットにまとまっている。
- 「期限ちょうどの瞬間も猶予中とみなす」「遷移のたびに期限を取り直す」の 2 つの書き換えは、どちらのブランチのテストでも検出できた。

## ラウンド 3 の結果

どちらの実装にも並行処理のバグがなかったので、両ブランチに同じ欠陥を仕込んだ。複数のリクエストを一括で処理するメソッドを足すコミットで、状態を読んでから書き戻すまでがアトミックでない。順番に呼ぶだけのテストは通る。そのうえで、次の報告文だけを渡した。

> 本番で、Free プラン（10 席）のスペースなのに、付与が 11 件成功として返ってきた。あとで見ると保有者は 10 人で、成功が返ったうちの 1 人にはライセンスが付いていなかった。一括付与と通常の付与が同じ時間帯に走っていたらしい。直して。

| | `plain` | `pstack` |
| --- | --- | --- |
| `src` の差分 | 2 ファイル、+63 / −14 | 2 ファイル、+38 / −10 |
| コミット | 1（テストと修正が一緒） | 2（失敗する再現テスト、その上に修正） |
| 再現テスト | 実スレッドの競争を 300 回くり返す 2 件 | 割り込む位置を固定した 1 件 |
| 使ったサブエージェント | 1（約 8 万トークン、約 1 分） | 1（約 12 万トークン、約 6 分） |

- 原因の特定と直し方は同じだった。無条件の書き戻しが原因で、通常の処理と一括処理を 1 つの compare-and-set ループに通す形に直している。あと付けのチェックで隠す修正にはならなかった。
- `pstack` の再現テストは、一括処理の途中で通常の付与が必ず割り込むように順序を固定しているので、タイミングに左右されない。修正前のコードで 3 回中 3 回失敗し、修正後は 3 回中 3 回通った。
- `pstack` は書き戻しに計測を入れ、壊れた回数と「変化した状態を上書きした回数」が 2000 回中どちらも 1079 回で一致することを示してから直している。
- `plain` は、上書きされたリクエストの再送記録も消えることをテストにした。`pstack` はこの点をコードから推測しただけで、テストしていない。

## 3 ラウンドを通して

| | `plain` | `pstack` |
| --- | --- | --- |
| サブエージェントのトークン合計 | 約 24 万 | 約 83 万 |
| 最終的な本体の行数 | 203 | 131 |
| コミット数 | 3（と仕込みの 1） | 17（と仕込みの 1） |

- 設計の骨格、原因の特定、テストの検出力は、3 ラウンドとも差がなかった。
- 差が出たのは、変更の小ささ、コミットの刻み方、主張に実行結果が付いているかの 3 点。
- 同じ課題を 3 つ並行に作らせる arena は、2 回とも候補がほぼ同じ形に収束した。この規模の課題ではコストに見合わなかった。
